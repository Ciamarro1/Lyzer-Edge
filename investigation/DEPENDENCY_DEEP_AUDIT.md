Both `@lyzer/shared` and `@lyzer/constitution` have **empty** `dependencies` in their `package.json`, yet they import npm packages:

| Imported Package | Files |

These work via npm workspace hoisting, but violate the principle that each package should declare its own dependencies. If the workspace layout changes or a consumer installs only one package, imports will fail.

## Finding 4 — Dual Lockfile Drift

| Lockfile | Location | Status |
|----------|----------|--------|
| `package-lock.json` | root | **Active** — correctly models the workspace with `"workspaces": ["packages/*", "lyzer edge"]` |
| `lyzer edge/package-lock.json` | `lyzer edge/` | **Stale duplicate** — standalone lockfile for `lyzer-edge-analyst` without workspace awareness |

The root `package-lock.json` is the authoritative one. The inner `lyzer edge/package-lock.json` is **not a workspace lockfile** — it was generated by running `npm install` inside the subdirectory. This causes two issues:

1. **Version divergence:** The inner lockfile contains an independent (possibly older) resolution tree.
2. **Confusion for tools:** Tools scanning for lockfiles may read the wrong one.

**Action:** Delete `lyzer edge/package-lock.json`.

## Finding 5 — Missing `"type": "module"` in Root `package.json`

Root `package.json` does **not** have `"type": "module"`, but these root-level files use ES module `import` syntax:

- `run_decision_quality_audit.js`
- `run_final_truth_audit.js`
- `run_final_independent_review.js`
- `run_real_replay_validation.js`
- `run_autonomous_research_lab.js`
- `run_institutional_committee_synthesis.js`
- `run_runtime_parity_experiment.js`
- `run_runtime_fidelity_audit.js`
- `run_simplification_execution.js`
- `run_simplification_audit.js`
- `reproduce.js`

These will fail at runtime with `SyntaxError: Cannot use import statement outside a module` unless run with `node --input-type=module` or the CJS `require` shim is used.

**Action:** Add `"type": "module"` to root `package.json`, or rename all root-level scripts to `.mjs`.

## Finding 6 — Workspace Packages Not Imported by Name

Despite both workspace packages having correct `"main": "src/index.js"` and being symlinked into `node_modules/@lyzer/`, **zero** import statements use the package name:

```
grep: from '@lyzer/shared'       → 0 matches
grep: from '@lyzer/constitution' → 0 matches
```

All 100+ imports use relative paths like:
```
../../packages/lyzer-shared/src/smc/replayEngine.js
../../packages/lyzer-constitution/src/eca/court.js
```

This means the `"main"` entry points are unused. If the internal file structure changes, all imports break. **Recommendation:** Migrate to package-name imports where possible.

---

## Finding 7 — Transitive Dependency Bloat

`@opentelemetry/api` appears in `node_modules` as a transitive dependency of `prom-client`. This adds 50+ KB of OpenTelemetry instrumentation code that is **only used in one file** (`metricsRegistry.js`) and only loaded dynamically via `await import()` with a try/catch fallback.

Other heavyweight transitive deps:
- `protobufjs` — pulled in by `@grpc/proto-loader` (certification scripts only)
- `tweetnacl` — pulled in by `nkeys.js` → `nats` (certification scripts only)
- `sqlite3` native addon — `node-gyp` rebuild required, 4+ MB

---

## Finding 8 — Duplicate Package Installations (Node Modules Layout)

Since npm workspaces hoist everything to root `node_modules/`, there are **no duplicate copies** of any package on disk. This is correct behavior. However, the inner `lyzer edge/package-lock.json` (if used) would create an isolated `lyzer edge/node_modules/` with a completely separate installation.
